- иметь необходимые лицензии/сертификаты (в т.ч. по ИБ, PCI DSS при приеме платежей, если применимо);

- предоставить план внедрения с интеграциями и сайзингом инфраструктуры (без привязки к конкретному вендору);
- обеспечить обучение пользователей и передачу документации (пользовательской и технической);
- соблюдать требования ИБ и законодательства о персональных данных.

### 1.3 Основание для разработки

- Договор между Заказчиком и Исполнителем.
- Внутренние стандарты Заказчика по ИБ.

- Требования PCI DSS при обработке платежных данных (если платежи проходят на стороне Платформы).
- Регламенты магазинов App Store/Google Play для публикации мобильных приложений.

### 1.4 Сроки

Начало работ — по подписанию договора.

Общий срок создания первой версии (MVP) — не более 3 месяцев, полный релиз с интеграциями — до 6 месяцев, если не оговорено иначе договором.

### 1.5 Порядок оформления и предъявления результатов

## 2. Назначение и цели создания Платформы

### 2.1 Назначение

«MyCafe» — мультиарендная no-code платформа для ресторанов, позволяющая:

- выпускать брендированные клиентские приложения (iOS/Android/Web) без программирования;
- управлять меню, заказами, бронированиями, программой лояльности, оплатами и аналитикой;
- автоматизировать работу персонала (официанты, кассиры, кухня, зал) и интегрироваться с внешними системами (POS, платежные шлюзы, CRM, доставочные сервисы).

### 2.2 Цели

- Сократить стоимость и срок выхода ресторана в мобильные каналы.
- Обеспечить единый цифровой контур: меню — заказ — оплата — доставка/самовывоз/к столу — лояльность — аналитика.
- Предоставить визуальные конструкторы (меню, экраны, бренд, промо, посадка столов).
- Обеспечить прозрачную систему скидок/кэшбэка/бонусов/промокодов.
- Предоставить API/интеграции для POS/CRM/доставок, шину событий, webhooks.
- Обеспечить масштабируемость и безопасность обработки заказов 24/7.

## 4. Требования к Платформе

### 4.1 Общие требования

- Архитектура: трехуровневая клиент — сервер приложений — сервер БД; микросервисная/модульная; мультиарендность (multi-tenant).
- Единая централизованная БД/кластер БД с изоляцией данных арендаторов.
- Единый механизм аутентификации/авторизации (поддержка SSO OAuth 2.0/OIDC, JWT).
- Кроссплатформенность: Web (современные браузеры), iOS/Android (актуальные версии).
- Мультиязычность интерфейсов (минимум: русский, английский; по требованию: локализация).
- Масштабируемость по нагрузке (горизонтально), наблюдаемость (логирование, трассировка, метрики).
- Высокая доступность (целевой SLA 99.5%+ для производственной среды, без учета плановых работ).
- Соблюдение ИБ, защиту персональных данных, защиту платежных данных (при необходимости — PCI DSS SAQ A/A-EP).

##### 4.1.1.1 Назначение основных подсистем

- **Администрирование Платформы**: управление арендаторами, тарифами, лимитами, аудитом, доступом, конфигурацией интеграций по умолчанию.
- **ИБ**: политики паролей/2FA, RBAC/ABAC, шифрование PII в покое и в транзите (TLS 1.2+), контроль соответствия.
- **Справочники/классификаторы**: унификация данных и валидаторов.
- **Шина данных**: событийно-ориентированное взаимодействие между сервисами и внешними системами, гарантированная доставка, идемпотентность.
- **Отчеты и аналитика**: финансовые, операционные, маркетинговые, когортный анализ, удержание, LTV, NPS/оценки.
- **Генерация приложений**: конвейер сборки white-label iOS/Android/Web, управление сертификатами, профилями, bundleId/keystore.

##### 4.1.1.2 Режимы функционирования

- **Штатный режим** — 24/7.
- **Ограниченный режим** — при частичной недоступности внешних интеграций, работа в деградированном режиме (например, прием заказов без онлайн-оплаты).
- **Сервисный режим** — плановые работы по регламенту (с уведомлением).
- **Аварийный режим** — согласно плану реагирования на инциденты (IRP), с восстановлением из резервных копий при необходимости.

#### 4.1.3 Требования к надежности

- Высокая доступность сервисов (кластеризация/автоскейлинг).
- Резервное копирование: ежедневные инкрементальные, еженедельные полные, хранение не менее 30 дней; тест восстановления не реже 1 раза в квартал.
- Устойчивость к сбоям: отказоустойчивые БД (репликация), очереди, кэш.
- Журналирование, алертинг, SLO/ошибки и латентность контролируются.
- Дозащита от ошибочных действий пользователей (подтверждения, soft delete, версии).

#### 4.1.4 Требования безопасности

- Аутентификация: email/телефон+пароль, соц. входы, 2FA (опционально).
- Авторизация: ролевая (RBAC), возможно атрибутивная (ABAC).
- Шифрование: TLS 1.2+, шифрование PII/секретов на хранении (KMS/HSM).
- Сегментация данных арендаторов; запрет утечек между арендаторами.
- Соответствие ISO/IEC 27001/27002; OWASP ASVS/MASVS; PCI DSS SAQ A при редиректе на платежного провайдера.
- Антифрод/скоринг по заказам (базовый), защита от бот-трафика (reCAPTCHA/ковенанты).
- Логи аудита (кто, что, когда изменил), неизменяемые журналы (WORM) по критичным операциям.

##### Сценарии нагрузочного тестирования

- Пользователи: 1000 одновременных
- Длительность: 30 минут
- Сценарий: просмотр меню, создание заказов, оплата
- Целевые метрики:
  - P50 latency < 300ms
  - P95 latency < 800ms
  - Error rate < 0.1%

**2. Stress Testing (пиковая нагрузка)**
- Пользователи: постепенное увеличение до отказа
- Цель: определить точку отказа системы
- Проверка автоскейлинга
- Проверка graceful degradation

**3. Spike Testing (внезапные скачки)**
- Моделирование: старт акции, lunch time peak
- Резкое увеличение нагрузки в 5-10 раз
- Проверка поведения очередей
- Проверка rate limiting

**4. Soak Testing (длительная работа)**
- Длительность: 24-48 часов
- Нормальная нагрузка
- Проверка утечек памяти
- Проверка накопления ошибок
